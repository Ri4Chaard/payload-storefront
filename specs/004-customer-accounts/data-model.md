## `customers`

Exists today at `src/collections/customers.ts` as "a door frame, not a door" — `auth: true`, an
owner-scoped read and update, `create: isAdmin`, and a single `name` text field. Its doc comment
lists registration, verification codes, password reset and profile screens as "deliberately absent
… those are the customer accounts spec". This is that spec.

### Auth configuration

| Key | Value | Requirement |
| --- | --- | --- |
| `verify` | `{ generateEmailHTML, generateEmailSubject }` | FR-004, FR-007 — and the interception point in R3 |
| `forgotPassword` | `{ expiration, generateEmailHTML, generateEmailSubject }` | FR-018 |
| `maxLoginAttempts` | `10` | FR-014 |
| `lockTime` | `900_000` (15 minutes) | FR-014 |
| `tokenExpiration` | `2_592_000` (30 days) | FR-012 — Payload's default of 7200s would sign customers out every two hours |

Turning `verify` on is what makes Payload's login throw `UnverifiedEmail` rather than succeeding
(`dist/auth/operations/login.js:184`), which is the mechanism behind FR-011's one permitted
disclosure: an unverified customer is routed to the verification step.

### Access

| Operation | Before | After | Why |
| --- | --- | --- | --- |
| `create` | `isAdmin` | `publicAccess` | FR-001. This is the door opening. Registration is the only public write in the feature. |
| `read` | admin, or own row | unchanged | FR-026 |
| `update` | admin, or own row | unchanged | FR-026 |
| `delete` | `isAdmin` | unchanged | FR-040 — erasure is an owner-operated path, not a self-serve button this feature draws |

No `admin` key, unchanged: a customer is never an admin-panel identity (FR-039). The boundary stays
structural — `admins` and `customers` are separate collections — rather than a role check.

### Fields

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `firstName` | text | no | FR-024. Split from the existing single `name`. |
| `lastName` | text | no | FR-024 |
| `name` | text | no | **Existing.** Retained and maintained by a `beforeChange` hook as `firstName + ' ' + lastName`, so `useAsTitle`, `defaultColumns` and the seller's existing view of a customer keep working. Not removed — a populated field cannot be dropped without a migration for no gain (Constitution IV). |
| `marketingEmail` | checkbox | no, defaults `false` | FR-036. **Default off** — the answer to the spec's one clarification. |
| `marketingEmailUpdatedAt` | date | no | FR-034. Maintained by a hook, never by the client, so the evidence cannot be forged from a form post. |
| `marketingEmailSource` | select — `registration`, `profile` | no | FR-034. Where the current choice was made. |

**Field-level access**: `marketingEmailUpdatedAt` and `marketingEmailSource` are `update: () => false`
for everyone. They are written by the hook that observes `marketingEmail` changing. A consent record
a customer can set to any timestamp is not evidence of anything.

**What is deliberately absent**: `phone` and a messenger handle. Brief FR-032 lists them; no frame in
this design draws them, and a messenger handle is only used by the request-and-handoff spec. Adding
fields no screen fills is how a content model rots.

### Hooks

| Hook | Does |
| --- | --- |
| `beforeChange` | Recomposes `name` from `firstName`/`lastName`. Stamps `marketingEmailUpdatedAt` and `marketingEmailSource` when, and only when, `marketingEmail` actually changes value. |
| `afterChange` | Syncs the Resend audience contact when `marketingEmail` changed, and on first verification (R2). Failure is logged and does not fail the write — a consent change must not be lost because a third party was down; a reconciliation pass is the repair, not a rollback. |

## `addresses`

**Not created here.** The e-commerce plugin generates it regardless of the `addresses: false`
currently in the config, it is already in `src/payload-types.ts:452`, and its table is already in
the committed migrations. See [research.md](./research.md) R5 for the verification. This feature
replaces `addresses: false` with a configuration object.

### Inherited from the plugin, unchanged

- `customer` — relationship to `customers`, sidebar-positioned.
- `access` — `create: isAuthenticated`, and `read`/`update`/`delete` composed as admin-or-owner.
  This is FR-032 satisfied by the plugin's own configuration.
- A `beforeChange` hook assigning `customer` from the request user, so ownership is never client-supplied.
- `country` promoted from text to a `select` over `supportedCountries`.
- `admin.hidden: true`.

**One correction required** (R7): `access.isAuthenticated` is not among the six functions
`src/payload.config.ts` passes, so `create` is silently undefined today. `isAuthenticated` is added
to `src/lib/access.ts` and passed.

### Fields added via `addressFields`

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `apartment` | text | no | FR-027, FR-030. "Apartment, suite, etc (optional)" in the design. |
| `isDefault` | checkbox | no, defaults `false` | FR-031 |

### Fields whose `required` changes

The plugin's defaults are all optional. FR-030 requires four of them:

| Field | Required | Optional |
| --- | --- | --- |
| `country` | ✅ (already required by the plugin) | |
| `addressLine1` | ✅ | |
| `city` | ✅ | |
| `postalCode` | ✅ | |
| `addressLine2` | | ✅ |
| `apartment` | | ✅ |

The design's error frame (`525:12889`) flags `Apartment` as invalid while its own placeholder says
"optional". Treated as a drawing slip — `apartment` is optional, per FR-030.

### Fields present but not surfaced

`title`, `firstName`, `lastName`, `company`, `state`, `phone`. The design draws none of them. They
remain in the schema because removing plugin-owned populated fields costs a migration and buys
nothing. Recorded so their absence from the form reads as a decision.

### `supportedCountries`

Replaced with the full ISO 3166-1 alpha-2 list (R6). The plugin's 40-entry default contains neither
Kazakhstan nor the UAE, so the shop's own market and the design's own sample address would both be
unsaveable. Labels come from `Intl.DisplayNames`, not from a hardcoded English list.

### The default-address invariant

FR-031 — exactly one default at any time — is enforced in a collection hook, not in the form.

**The mechanism**: `addresses.addressesCollectionOverride`, which the plugin exposes for exactly
this (`dist/types/index.d.ts:449`) and which is the same `*CollectionOverride` pattern already used
for `products`, `variants` and `carts` in `src/payload.config.ts`. Fields go through `addressFields`
— the plugin's own comment says that is "preferred use over the collectionOverride config" because
those fields also propagate to Orders and Transactions — and only the hooks go through the override.

| Event | Effect |
| --- | --- |
| First address saved for a customer | `isDefault` forced true |
| An address saved with `isDefault: true` | Every other address for that customer is cleared |
| The default deleted, others remain | The most recently created remaining address is promoted |
| The last address deleted | Nothing to promote |

In a hook because two tabs, the admin panel, and a future checkout are all writers. An invariant
enforced in one form is an invariant that holds until the second writer appears.

## `verification-codes` — new

The only genuinely new collection. It holds the code→token indirection from R3.

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `email` | text | ✅ | Indexed. What throttling and lookup are keyed on. Stored independently of `customer` so a code survives to be refused after an account is purged. |
| `customer` | relationship → `customers` | no | Convenience for the admin; never the lookup key. |
| `purpose` | select — `verify-email`, `reset-password` | ✅ | A code minted for one purpose must never satisfy the other. |
| `codeHash` | text | ✅ | The hash of the six digits. Never the digits (R4, FR-038). |
| `token` | text | ✅ | Payload's own verification or reset token. The thing the code is an alias for. |
| `expiresAt` | date | ✅ | Issue time + 10 minutes |
| `attempts` | number | ✅, default `0` | Burns the code at 5 (FR-005) |
| `consumedAt` | date | no | Set on success. Single-use (FR-005). |
| `supersededAt` | date | no | Set when a newer code is issued for the same email and purpose (FR-005). |

### Access

Every operation is `() => false`. Nothing — no customer, no admin, no public request — reads or
writes this collection through the API. It is touched only by server-side code using the Local API
with `overrideAccess: true`.

This is the strictest access block in the codebase and it is deliberate: the collection holds live
credentials. `admin.hidden: true` for the same reason. Constitution IV asks for access to be a
deliberate decision; this one is "nobody".

### State

```
                 issued
                   │
   ┌───────────────┼────────────────┬─────────────────┐
   ▼               ▼                ▼                 ▼
consumed       expired          attempts = 5      superseded
(success)   (expiresAt past)   (five wrong)    (newer code issued)
```

Four terminal states, one success. Every non-terminal read must check all four — which is why the
check lives in one function (`contracts/auth-actions.md`) and not at each call site.

### Retention

Rows are deleted by the scheduled task (R15) once terminal and older than 24 hours. A spent code is
not evidence of anything worth keeping, and FR-040 wants a documented retention period for every
collection point.

## `account-settings` — new global

What the copy global should have been. Three values, all of them decisions about the shop rather
than sentences about a screen, grouped into two tabs under **Shop** beside **Shop settings**.

| Tab | Field | Holds |
| --- | --- | --- |
| Addresses | `defaultCountry` | Pre-selected when a customer adds an address (FR-030, R6). `NOT NULL`, defaults to `AE` |
| Addresses | `shippingCountries` | Which countries the form offers. Empty means all |
| Marketing | `marketingEnabled` | Whether the registration form asks for consent at all |

**Narrowing `shippingCountries` cannot invalidate stored data.** It changes what the form *offers*;
the column keeps the full ISO enum, so an address already saved in a country later removed from the
list stays valid rather than becoming unsaveable. Same widening argument as `addresses.country`,
applied in the one direction that is safe.

**`marketingEnabled` never touches transactional mail.** Verification codes and password-changed
notices are sent regardless — FR-035 is a property of the module split (R2), not of this flag.

**Read through `resolveAccountSettings`**, never directly: every field on the generated type is
nullable, because Payload cannot promise the row exists before anyone saves it. The fallbacks are
resolved in one place so three call sites cannot disagree about the default.

**Access**: `read: () => true`, `update: isAdmin`. Same shape as `Shop`.

```
customers ──1:N──> verification-codes (convenience only; lookup is by email + purpose)
customers ──1:N──> carts              (existing, unchanged)
```

Nothing in this feature relates to `products`, `variants`, or the catalogue.

## Migration

One generated, committed migration with a tested `down`, per Constitution IV.

**Adds**: five columns on `customers`; two columns on `addresses`; the `verification_codes` table
and its indexes. (It also added the `account` table, dropped again two migrations later — R11.)

**Alters**: `addresses.country` — the `select` regenerates its enum with the full ISO list. This is
the only alteration touching an existing column, and it is **widening**: every one of the plugin's
40 values remains valid, so no stored row can be invalidated. The `down` narrows it back, which is
safe only while no row holds one of the new values — recorded here because that is exactly the kind
of rollback that fails at 2am against production data, and the quickstart's rollback check must run
with a Kazakhstan address present to prove the behaviour is understood.

**No data backfill.** `firstName`/`lastName` are added empty rather than parsed out of the existing
`name`, because splitting a full name on whitespace is wrong often enough to be worse than an empty
field the customer fills in themselves. There are no production customers yet — `create` has been
admin-only since the collection was written — so the population is empty in any case.
